### 実測値（Twilio が公式に文書化していない項目）

|---|---|---|
| 1フレームのバイト長 | **160 バイト** | 1071 / 1071 フレームすべて。ばらつきなし |

| フレームレート（timestamp基準） | **49.64 fps** | — |
| フレームレート（実時間基準） | **48.77 fps** | — |

### 再生バッファ深度（レイテンシ）

`mark` の往復時間を 41 サンプル測定した。

| 指標 | 値 |
|---|---|
| 最小 | 652 ms |
| 平均 | **666 ms** |

**重要な点は、この値が通話中ほぼ一定であること。** 送信バッファが累積していく

## 既知の制約事項（Stage 1 時点）

### 設計上の制約

- **音声フォーマットは G.711 μ-law 8kHz mono 固定。** Twilio Media Streams に選択肢はない。
- **Media Streams に日本リージョンが存在しない**（US1 / IE1 / AU1）。
  Console の `tokyo` は SIP/REST 用の Edge Location であって Media Engine の位置ではないため、
  サーバーを東京に置いても音声経路は短くならない。
- **Twilio Console の Debugger に毎通話 31921 が ERROR として記録される。**
  これはサーバーが WebSocket を閉じた記録であり、仕様上正しい終了手順である。異常ではない。

### レイテンシ予算（Stage 2 に向けた注意）

Twilio が公表している音声AIエージェントの目標は mouth-to-ear 往復 1,115ms、上限 1,400ms。
本測定ではパイプラインが空の状態で既に **約 666ms** を消費している。
OpenAI が音声を認識し、応答を生成し、発話を開始するまでの時間はこの残余（約450ms）に収まらない。

**対策: サーバーを US East に設置する。** 太平洋横断を2回削減でき、200〜300ms 程度の
改善が見込まれる。Stage 2 のレイテンシ評価はこの変更後に行うべきである。

### 未検証事項（今後の Stage で確認する）

| 項目 | 状況 |
|---|---|
| `</Connect>` 後の `<Say>` の再生 | **未検証。** 今回は発信者が切断したため Twilio 側から `stop` が来た。サーバー側からソケットを閉じる経路（Stage 5 の終話フロー）は未通過 |
| `X-Twilio-Signature` の検証 | **未実施。** Auth Token 未入手のため `TWILIO_SIGNATURE_MODE=log` でスキップ。トークン設定後に検証し `enforce` へ切り替える |
| 長時間通話での挙動 | 22秒のみ確認。受付フロー全体（3〜5分）での安定性は未検証 |
| 無言が続く通話の維持 | 未検証。トンネル／プロキシのアイドルタイムアウトの影響を受ける可能性 |
| Twilio からの WebSocket ping | 今回の通話では受信を確認できず |
| 同時通話 | 単一通話のみ。デモ要件外だが未検証 |

### 運用上の注意

- Cloudflare Quick Tunnel の URL は再起動のたびに変わる。変わった場合は
  Twilio 番号の Voice Webhook を貼り直す必要がある（コード側は Host ヘッダから自動追従するため修正不要）。
- 番号のフレンドリー名に、他用途で使用中である旨の表示があった。Voice Webhook は
  空だったため実際の利用はなかったと判断したが、他用途と競合しないか運用前に
  確認することが望ましい。
- 日本の携帯電話の「かけ放題」プランは 050 番号を対象外とすることが多く、
  テスト通話は通常課金される。

## Stage 2 / Stage 3: AI応答と項目取得

### Stage 2（会話の疎通）— 2026-09-10 実施・合格

| 項目 | 結果 |

日本語で自然に会話でき、以下が実機で確認できた。

- マンション名「ライオンズマンション」を 8kHz 越しに正しく認識し復唱
- お名前を**かな**で取得し復唱確認
- 仮予約日を**曜日付き**で案内（9月24日、木曜日 — 曜日計算も正しい）
- 数字の「7」を**なな**と読む（「じゅうななじ」）
- 「17時」を「午後5時」と自ら言い換えて曖昧さを排除

**音声デルタのイベント名は `response.output_audio.delta`（GA名）であることを実測で確定。**
beta 名 `response.audio.delta` を待つ実装だと、エラー無しの完全な無音になる。

**`audio_end_ms` の安全弁が実通話で2回発動**（9580→9100 / 12220→11650）。
経過時間が生成済み音声長を超えた場合に頭打ちにする処理で、これが無いと
サーバーエラーになる。Twilio 公式サンプルにはこの上限が無い。

検出した課題（Stage 3 で対処済み）:
- VAD が過敏。9回の barge-in のうち3回が2秒未満（最短160ms）で AI を誤って中断
- 1ターンが約10秒と長く、毎ターン社名を名乗り直していた
- データモデルに無い「工事開始時間」を勝手に聞き出していた

取得内容はいずれも `{name_kana:"やまだ たろう", phone:…, building:"ライオンズマンション", room:"305"}` で、
**1項目ずつ順に**記録された（まとめて1回で呼ばれることはなかった）。

**レイテンシの測り方**: `input_audio_buffer.speech_stopped`（発信者が話し終えた時点）から
AI の最初の音声チャンクが**自サーバーに届く**までの時間。発信者の耳に届くまでには
さらにサーバー→Twilio→再生バッファ→PSTN の片道が加算されるため、体感値はこれより大きい。
Stage 1 の mark 往復実測（平均666ms）から、片道はおおむね300〜400ms と見積もられる。

**VAD 調整の効果**: `VAD_THRESHOLD` を 0.5→0.65 に変更した結果、
2秒未満の誤った中断は 3/9 → 1/4 → 0/5 と減少した。

**マンション名の3択制約が実機で機能**: 候補外の名称に対して AI はツールを呼ばず聞き返し、
3回失敗した時点で「お電話が遠いようですので、改めておかけ直しいただけますでしょうか」と
丁寧に終話を促した（CLAUDE.md のエラー処理要件どおり）。その後、正しい名称で復帰している。
**モデル側のゲートで止まったため、サーバー側の検証は発火しなかった**（多層防御の外側が機能）。

## 既知の制約事項（Stage 3 時点で追加）

| 項目 | 内容 |
|---|---|
| **電話番号の検証は桁数のみ** | CLAUDE.md の仕様どおり10〜11桁で検証している。そのため携帯番号（070/080/090）で1桁不足した「090-1234-567」（10桁）は、固定電話として妥当な桁数のため**受理される**。携帯プレフィクスなら11桁必須とする追加検証は仕様範囲外のため未実装。必要なら要相談 |

### 検出した不具合（修正済み）

| 不具合 | 原因 | 対処 |
|---|---|---|
| 締めの挨拶が途中で切れる（3通話中2通話） | 終話の保険が固定20秒。OpenAI は実時間より速く音声を生成するため、復唱が長いと Twilio の再生待ち行列が数十秒ぶんたまる（実測で mark 48個＝約9.6秒ぶんが未再生） | mark の返りが止まったことを終了条件とする適応式ウォッチドッグへ変更 |

| 「変更希望」の第一希望に仮予約日と同じ日を記録 | 状態機械が仮予約日を知らなかった | `ReceptionState` に仮予約日を渡し、同一日を拒否 |
